# EVALUATION.md（tune）

業務アプリ向けの仕様評価は使わない。競技ではマニュアルとベンチマーカーが評価基準。

## 評価目標

最終走行で高い有効スコアを得る。**最高スコアを出した実装と、最後に提出されるスコアは別**。

## 評価項目

### 正常性
- ベンチマークの検証に合格する（不合格ならスコア 0 として扱う）
- 必須機能が正常に動作する（`commands.regression` があればベンチ前に実行）
- 再起動後も必要なデータが保持される（終盤に `final_run.py check`）

### 性能
- スコア
- スループット、p95 / p99 レイテンシ、HTTP エラー率（ベンチマーカー出力・アクセスログ）
- CPU / メモリ / I/O（プロファイル）

### 改善の判断（benchmark.py が判定する）
- 最良（コミットごとの有効スコアの中央値）と最新を区別する
- 改善幅が `noise_pct` 以下なら断定しない（RETEST → 同じ構成で再測定）
- 1 回でも正常性検証に落ちたコミットは採用しない
- すべての走行をコミット・時刻・フェーズ・ログと紐づけて `benchmarks.jsonl` に残す

### 停滞
最高スコアが 30 分間更新されない場合、Hook が Critic による監査を促す。
Critic の提案は無条件に採用せず、測定で確かめる。

### 終盤（残り 40 分）
- 提出する版に揃える（通常は最良コミット。`tools/restore.sh`）
- すべてのサーバーの再起動を検証する
- 永続データを検証する
- `final_run.py check` を通す

### 最終走行
- ベンチを実行するたびに `final_run.py decide` を実行する
- 同じコミットのスコア分布と残り時間から STOP / RUN を判断する
- STOP 後はベンチ・デプロイ・変更をしない（guard.py が拒否する）

## 誰が判定するか

| 判定 | 仕組み |
|---|---|
| スコア・正常性・採否 | `evaluator/benchmark.py`（プログラム） |
| 停滞の検出 | `plugin/hooks/stagnation.py`（プログラム） |
| 停滞時の仮説の見直し | Critic（LLM） |
| 終盤の検証・停止判断 | `evaluator/final_run.py`（プログラム） |
| 改善の方針・実装 | メインエージェント |
